# RAG 技术架构报告 (2025-12-12)

## 1. 执行摘要

本报告旨在评估 InfinityNoteX 中检索增强生成 (RAG) 系统的现状。目前该系统处于 **最小可行性产品 (MVP)** 阶段，能够利用向量嵌入来实现基于笔记上下文的 AI 对话功能。

**当前状态**: 🟢 功能性 MVP

- **Embedding**: 支持 OpenAI 兼容的 API（暂无本地模型）。
- **存储**: 基于本地 JSON 文件的内存向量存储。
- **检索**: 基础余弦相似度搜索 (Top-K)。
- **集成**: 已完全集成到前端 `AIChat` 组件中。

**核心发现**:

- 架构具有模块化特性，但目前在大规模知识库场景下缺乏扩展性。
- 架构上支持增量索引（实时更新），但尚未实现笔记变更后的自动触发机制。
- 尚未实现本地隐私优先的 embedding 方案（这是原始计划中的关键目标）。

---

## 2. 系统架构

RAG 系统采用解耦架构，将主进程（索引/Embedding）与渲染进程（UI/交互）分离。

### 2.1 核心组件

| 组件                 | 位置                              | 职责                                                                                                                                    |
| -------------------- | --------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| **EmbeddingService** | `electron/embedding.ts`           | 处理与外部 Embedding API（如阿里云百炼、硅基流动）的通信。实现遵循 OpenAI 标准 (`/v1/embeddings`)。处理批处理和速率限制 (429 重试)。    |
| **KnowledgeIndex**   | `electron/knowledgeIndex.ts`      | 核心索引逻辑。1. 从 TipTap JSON 提取文本。2. 文本分块 (窗口: 500字符, 重叠: 50)。3. 管理 `InMemoryVectorStore`。4. 执行余弦相似度搜索。 |
| **StorageManager**   | `electron/storage/*`              | 管理原始笔记文件。_注意：目前与 KnowledgeIndex 解耦 - 笔记更新不会自动触发重新索引。_                                                   |
| **AIChat Logic**     | `src/components/AIChat/*`         | 前端 Hook `useAIChat.ts` 编排流程：用户输入 -> IPC `search` -> 上下文注入 -> LLM 流式输出。                                             |
| **IPC Bridge**       | `preload.ts` (`window.knowledge`) | 暴露安全的 API 端点：`search`, `rebuildIndex`, `getStats`, `setConfig`。                                                                |

### 2.2 数据流

1. **索引 (写入路径)**
   - _触发_: 手动 "重建索引"（当前）或同步。
   - _流程_: `StorageManager` -> 文本提取 -> 分块 -> Embedding API -> 向量 + 元数据 -> `vector-index.json`。
2. **检索 (读取路径)**
   - _触发_: 用户在开启 "知识库" 的情况下发送 AI 消息。
   - _流程_: 查询文本 -> Embedding API -> 向量 -> `InMemoryVectorStore.search()` -> Top 3 结果。
3. **生成**
   - _流程_: Top 结果被格式化为 `[来源 {i}: {标题}] \n {内容}` 并追加到 Prompt 中，然后发送给聊天 LLM。

## 3. 实现现状与计划对比

将现有实现与 _便签 RAG 功能开发计划报告_ 进行对比。

| 功能领域      | 计划                               | 已实现 (当前)            | 状态        |
| ------------- | ---------------------------------- | ------------------------ | ----------- |
| **Embedding** | 本地 (Sentence-Transformers) & API | **仅 API** (OpenAI 协议) | ⚠️ 部分完成 |
| **存储**      | SQLite + Vector Ext / 本地 JSON    | **本地 JSON (内存加载)** | ⚠️ MVP      |
| **索引**      | 增量 / 实时                        | **手动 / 全量重建**      | ⚠️ 差距     |
| **检索**      | 语义搜索                           | **语义搜索 (余弦)**      | ✅ 完成     |
| **聊天集成**  | 上下文注入, 引用标注               | **上下文注入, 来源展示** | ✅ 完成     |
| **内容处理**  | 结构化提取                         | TipTap -> 纯文本         | 🟡 基础     |

### 局限性

1. **扩展性**: `InMemoryVectorStore` 会将整个 `vector-index.json` 加载到 RAM 中。对于 <10,000 条笔记尚可。对于更大的库，会导致内存问题和启动缓慢。
2. **延迟**: 创建 embedding 依赖外部 API 调用，给每条聊天消息和索引操作增加了网络延迟。
3. **实时性**: 编辑笔记不会立即更新其向量索引。用户必须手动重建或等待同步事件。

## 4. 建议与路线图

### 第一阶段: 优化 (立即执行)

1. **实时索引**: 在 `main.ts` 中挂载 `StorageManager` 事件 (`storage:event`)，在笔记保存时触发 `indexNote`。
2. **持久化升级**: 如果笔记数量 > 1000，替换 `vector-index.json` 为更健壮的方案，或优化 JSON 加载策略。
3. **检索优化**: 实现 `混合搜索` (关键词 + 向量)，使用简单的排序器提高检索质量。

### 第二阶段: 本地与隐私 (下一季度)

1. **本地 Embeddings**: 集成轻量级 ONNX 运行时或 Python Sidecar 以在本地运行 embedding 模型，移除 API 依赖。
2. **离线能力**: 确保 RAG 功能在无网络环境下完全可用（如果同时使用了本地 LLM）。

### 第三阶段:以此为基础的高级 RAG

1. **查询扩展**: 使用 LLM 重写用户查询，以提高检索的一致性。
2. **重排序 (Re-ranking)**: 在向量检索后增加重排序步骤，提高 Top-K 上下文的相关性。
