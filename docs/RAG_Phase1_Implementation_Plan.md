# RAG 第一阶段功能开发计划

> **版本**: v1.0\
> **创建日期**: 2025-12-12\
> **目标**: 提升 RAG 知识库的实时性、稳定性和检索质量

---

## 一、背景与目标

### 1.1 现状痛点

| 痛点                     | 用户影响                       | 严重程度   |
| ------------------------ | ------------------------------ | ---------- |
| 笔记更新后需手动重建索引 | 新写的笔记 AI 查不到，用户困惑 | ⭐⭐⭐⭐⭐ |
| 大量笔记时启动/索引慢    | 应用启动卡顿，重建索引耗时长   | ⭐⭐⭐     |
| 纯向量检索有时不准       | AI 引用的笔记与问题不太相关    | ⭐⭐⭐⭐   |

### 1.2 目标用户场景

1. **场景A - 即写即问**：用户刚写完一篇会议纪要，立刻问 AI "今天会议的关键决策是什么？"
2. **场景B - 知识库积累**：用户有 2000+ 篇笔记，使用 AI 进行跨笔记总结和问答。
3. **场景C - 精确检索**：用户问 "关于 API Rate Limit 的解决方案"，期望 AI 找到包含这些关键词的笔记。

### 1.3 成功指标

| 指标                   | 当前           | 目标          |
| ---------------------- | -------------- | ------------- |
| 新笔记可被检索延迟     | 需手动重建 (∞) | < 5 秒 (自动) |
| 1000 笔记索引加载时间  | ~3 秒          | < 1 秒        |
| Top-3 检索相关性满意度 | 约 60%         | > 80%         |

## 二、功能规划

### 功能 1：实时索引 (Real-Time Indexing)

#### 2.1.1 功能描述

当用户 **创建/编辑/删除** 笔记时，系统自动在后台更新该笔记在 RAG 知识库中的向量索引，无需用户手动操作。

#### 2.1.2 用户价值

- **"写完就能问"**：用户写完笔记后，立刻可以在 AI 对话中引用。
- **减少操作负担**：无需记住去 "重建索引"。

#### 2.1.3 功能细节

| 触发事件            | 系统行为                               | 用户感知      |
| ------------------- | -------------------------------------- | ------------- |
| 笔记创建            | 提取文本 -> 分块 -> 向量化 -> 写入索引 | 无感知 (后台) |
| 笔记更新            | 删除旧向量 -> 重新向量化 -> 写入索引   | 无感知 (后台) |
| 笔记删除            | 删除对应向量                           | 无感知 (后台) |
| 笔记恢复 (从回收站) | 同 "笔记创建"                          | 无感知 (后台) |

#### 2.1.4 边界情况处理

1. **Embedding API 不可用**：静默失败，记录日志，下次启动时统一补索引。
2. **频繁编辑同一笔记**：防抖处理，编辑停止 2 秒后才触发索引。
3. **批量导入/同步**：使用队列依次处理，避免 API 速率限制。

#### 2.1.5 技术方案 (简述)

```
graph LR
  A[StorageManager] --storage:event--> B[main.ts 事件监听]
  B --note:created/updated--> C[KnowledgeIndexService.indexNote]
  B --note:deleted--> D[KnowledgeIndexService.deleteNote]
  C --> E[EmbeddingService.embed]
  E --> F[VectorStore.upsert]
  D --> G[VectorStore.delete]
```

#### 2.1.6 开发任务

| 任务 | 描述                                                                  | 预估工时 |
| ---- | --------------------------------------------------------------------- | -------- |
| T1.1 | `main.ts` 监听 `storage:event`，分发至 `knowledgeIndex`               | 0.5d     |
| T1.2 | `knowledgeIndex.ts` 新增 `indexSingleNote` / `deleteNoteVectors` 方法 | 0.5d     |
| T1.3 | 防抖处理：笔记频繁编辑时延迟索引                                      | 0.5d     |
| T1.4 | 错误处理与日志：API 失败时的降级策略                                  | 0.5d     |
| T1.5 | 测试：创建/更新/删除笔记后 AI 检索验证                                | 0.5d     |

**小计**: 2.5 人天

### 功能 2：持久化升级 (Persistence Upgrade)

#### 2.2.1 功能描述

优化向量索引的存储方式，解决笔记数量增长后的性能问题。

#### 2.2.2 用户价值

- **启动更快**：打开应用时不再因加载大索引而卡顿。
- **内存更省**：减少应用运行时的内存占用。

#### 2.2.3 方案选型

| 方案                    | 优点               | 缺点                 | 适用场景     |
| ----------------------- | ------------------ | -------------------- | ------------ |
| **A. 分片 JSON**        | 实现简单，无新依赖 | 仍有内存压力         | < 5000 笔记  |
| **B. SQLite + JSON 列** | 查询快，易于扩展   | 需引入依赖           | < 50000 笔记 |
| **C. SQLite-vec 扩展**  | 原生向量搜索       | 编译复杂，跨平台问题 | 超大规模     |

**推荐方案**: **A. 分片 JSON** (短期) + **B. SQLite** (中期)

#### 2.2.4 分片 JSON 策略 (短期实现)

将 `vector-index.json` 拆分为多个小文件，按需加载：

```
/userData/knowledge/
├── index-meta.json       # 元数据：总笔记数、分片信息
├── chunks/
│   ├── shard-0.json      # 笔记 1-500 的向量
│   ├── shard-1.json      # 笔记 501-1000 的向量
│   └── shard-2.json      # ...
```

**加载策略**:

1. 启动时仅加载 `index-meta.json`。
2. 搜索时按需加载相关分片（或使用 LRU 缓存热门分片）。

#### 2.2.5 开发任务

| 任务 | 描述                                                 | 预估工时 |
| ---- | ---------------------------------------------------- | -------- |
| T2.1 | 重构 `InMemoryVectorStore`，支持分片读写             | 1d       |
| T2.2 | 实现分片懒加载与 LRU 缓存（最多保留 3 个分片在内存） | 1d       |
| T2.3 | 迁移逻辑：旧 `vector-index.json` -> 分片格式         | 0.5d     |
| T2.4 | 性能测试：1000/5000 笔记场景的启动时间对比           | 0.5d     |

**小计**: 3 人天

### 功能 3：混合搜索 (Hybrid Search)

#### 2.3.1 功能描述

在现有的 **向量语义搜索** 基础上，增加 **关键词搜索** 能力，并将两者结果融合排序，提高检索准确率。

#### 2.3.2 用户价值

- **专业术语更准**：用户问 "OAuth2.0 授权流程"，能精确命中包含 "OAuth2.0" 的笔记。
- **模糊意图更懂**：用户问 "最近项目进展"，能通过语义理解找到相关笔记。

#### 2.3.3 混合搜索原理

```
用户查询: "如何解决 API Rate Limit"
          ↓
   ┌──────┴──────┐
   ↓             ↓
关键词搜索     向量搜索
(BM25/模糊)   (余弦相似度)
   ↓             ↓
结果 A         结果 B
(Top 10)      (Top 10)
   └──────┬──────┘
          ↓
      融合排序
   (RRF / 加权平均)
          ↓
      返回 Top 3
```

#### 2.3.4 关键词搜索实现

由于我们已有笔记纯文本，可直接进行简单的关键词匹配：

1. **分词**：将查询拆分为关键词（中文使用简单空格/标点分割或 jieba）。
2. **匹配**：在笔记文本中统计关键词出现次数 (TF)。
3. **评分**：使用简化 BM25 或 TF-IDF 计算分数。

#### 2.3.5 融合排序算法 (RRF)

使用 **Reciprocal Rank Fusion** (RRF) 融合两路结果：

```
RRF_score(doc) = Σ 1 / (k + rank_i(doc))
```

其中 `k` 通常取 60，`rank_i` 是文档在第 i 路结果中的排名。

| 任务 | 描述                                              | 预估工时 |
| ---- | ------------------------------------------------- | -------- |
| T3.1 | `knowledgeIndex.ts` 新增 `keywordSearch` 方法     | 1d       |
| T3.2 | 实现简单分词器（支持中英文）                      | 0.5d     |
| T3.3 | 实现 RRF 融合排序逻辑                             | 0.5d     |
| T3.4 | 重构 `semanticSearch` -> `hybridSearch`，统一入口 | 0.5d     |
| T3.5 | A/B 测试：对比纯向量 vs 混合搜索的 Top-3 相关性   | 0.5d     |

**小计**: 3 人天

## 四、风险与应对

| 风险                               | 概率 | 影响 | 应对措施                   |
| ---------------------------------- | ---- | ---- | -------------------------- |
| Embedding API 调用过于频繁触发限流 | 中   | 高   | 增加队列 + 指数退避重试    |
| 分片 JSON 方案仍有性能瓶颈         | 低   | 中   | 预留 SQLite 方案接口       |
| 混合搜索融合权重不当               | 中   | 中   | 提供调试日志，便于后期调优 |

## 五、验收标准 (DoD)

### 功能 1: 实时索引

- [ ] 创建笔记后 5 秒内可被 AI 检索到
- [ ] 更新笔记后 AI 返回最新内容
- [ ] 删除笔记后 AI 不再引用该笔记
- [ ] 频繁编辑时不会触发过多 API 请求

### 功能 2: 持久化升级

- [ ] 1000 篇笔记的索引加载时间 < 1 秒
- [ ] 内存占用不超过 100MB (索引部分)
- [ ] 旧版 `vector-index.json` 可自动迁移

### 功能 3: 混合搜索

- [ ] 包含明确关键词的查询命中率 > 90%
- [ ] 主观评测 Top-3 相关性满意度 > 80%
- [ ] 搜索响应时间 < 500ms
